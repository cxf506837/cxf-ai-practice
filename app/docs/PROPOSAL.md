# 产品与技术方案 v1.0（用户已确认）

日期：2026-10-09，Asia/Shanghai。用户于20:06前确认方案并提供开发密钥、授权继续实施。以下首版边界和验收口径冻结；时间仍为估计，不是交付承诺。

## 目标与价值假设

目标用户是经常收到群通知、靠人工记住截止时间和材料要求的人。第一用户是本项目发起者。

用户提供群聊文本、自己的称呼/角色（可选）、消息日期背景（可选），获得带来源的候选任务，确认或修改后保存；追加通知时可以核对更正。价值应来自重复使用、原文追溯和任务状态，不是一次摘要。

价值闸门：S1 最小流程可用后、进入 S2 前，让用户试用三组自己会遇到的脱敏消息，比较直接交给 Codex 的人工修改次数、操作步骤和再次使用意愿，记录继续/调整/停止决定。若不愿再次粘贴、任务卡没有带来便利，停止扩展并讨论方向；不为了作品集强行证明需求。

## 三条路线

1. 推荐：本地运行的浏览器应用，文字输入，结构化任务与本地持久化。先独立可用，再决定公开展示方式。
2. 手机分享入口：输入方便，但增加平台适配；等文字流程证明价值后再讨论，不纳入首版。
3. 自动读取群聊并执行：依赖手机能力、权限和页面适配，容易再次失控，首版排除。

## 首版业务流程

1. 选择或新建来源名称（例如“班级群”，生成可重用 sourceId），粘贴文本，选择消息日期背景，必要时填写自己的角色。先预览要发给模型的内容，再显式点击分析。
2. 为导入文本建立记录 ID，并关联所选 sourceId；模型提取标题、适用对象、截止时间原文、材料清单、出处与疑点。
3. 程序验证来源确实存在、字段合法；无依据字段不自动接受。相对日期缺少基准时保留原文和待确认，不以导入日期猜测。
4. 展示候选卡：原文与提取结果并排；用户可修改、忽略或确认。没有任务是合法结果。
5. 确认后进入待办列表，支持完成/重新打开、编辑、删除和 JSON 导出；刷新后仍保留。删除需明确影响范围。
6. 首版仅保证同一 sourceId 下完全相同文本重复导入，以及同一候选重复确认的幂等。不同来源不合并。部分重叠、相似通知和更正由用户选择关联任务，展示新旧原文再确认修改；不承诺自动相似匹配。撤销通知只标为疑点，由用户确认后删除或编辑原任务，不自动改变已完成状态。

不包含 OCR、PDF、手机监听、外部自动执行、多用户协作、支付、后台推送、复杂多 Agent。先做手机宽度可用的页面，不先做原生 App。

## 技术路线（概念设计）

- 单仓库、单服务入口、单用户本地数据。前端负责文本、卡片和待办；服务端负责模型请求、结果校验和存储。原文、分析结果、确认任务有明确 ID 关联。
- 技术选择：React + Vite + TypeScript；服务端Node.js 24.19原生HTTP与node:sqlite，避免增加服务框架和原生编译驱动。包版本以安装后的package.json和锁文件为准，Node24.19为本地已验证运行时。当前会话没有可发现的Context7工具，采用React/Vite/Node官方文档。
- 模型只负责语义提取/更正候选；保存、去重、状态变化、导出由确定性代码执行。初版采用有边界工作流，不为了 Agent 名称加入自由执行循环。
- 应用模型与开发模型分离。开发：gpt-6.1-sol/high；升级与验收：gpt-6-astra/medium。应用选deepseek-flash，用户提供的密钥已保存本项目.env并通过官方/models接口验证，只在服务端使用。收费测试限制为合成消息、单次有界请求、无自动重试；报告实际用量，费率未核实不虚报金额。
- 没有应用 API 时先用明确标记的合成样例验证界面/数据流，不能计入真实模型验收。模型配置通过本地环境完成，不把密钥发送到浏览器或聊天。
- 模型失败、超时、非法响应：保留输入，显示失败原因，用户可重试；单次分析限制输入与请求预算，不无限重试。不把聊天原文当指令，不给模型外部写入工具。
- 本地数据在忽略目录内，不进入 Git；服务默认仅监听回环地址。模型仅收到预览列明的当前文本、日期背景及用户选择的角色，更正对比所需旧任务必须显式选择并在预览展示，不隐式发送历史资料。核实提供商数据条件前仅用合成数据；本地删除不代表供应商端删除。公开作品演示仅用合成数据；公开真实模型调用、多用户隔离、托管密钥与费用保护另行设计批准后才能上线。

## 初版验收建议（批准后冻结）

- 先固定 20 组人工核对标注的合成消息（10 开发、10 独立验收），覆盖普通通知、无关闲聊、相对日期、更正、撤销、重复、同名不同群、对象不明、缺材料、恶意文本。执行者只使用开发集；独立审查者持有验收标注，运行时冻结源码和提示。执行者知晓具体验收失败后，该用例变成回归案例，不再声称盲测；新独立样本由审查者补充，保留旧结果。
- 任务按来源及原文所指动作一对一匹配，不仅按标题字符串。正确匹配为 TP，多余或重复预测为 FP，漏掉的标注任务为 FN；精确率=TP/(TP+FP)，召回率=TP/(TP+FN)，按全验收集合并计数。三次运行每次两项都 >=90%，同时单列日期、适用对象、材料和出处断言；有明确依据的关键字段及不确定标记必须全部正确，不能用检出率遮盖字段错误。空样例有预测即 FP，无预测且无标注不贡献分母；分母为零报 N/A，不能算达标，应补充有任务样例。样本小，不宣传为真实世界准确率。
- 已接受任务的原文引用可定位；日期无依据不擅自确定；注入文本不触发外部动作；重复确认不会新增重复任务；刷新和导出内容一致。这些关键断言必须全部通过。
- 固定模型/配置的独立验收集重复三次，分别报告结果、耗时、用量、误报漏报；不能只挑最好一轮。失败样例保留，阈值修改必须说明并讨论。
- Astra 实际执行有限范围对抗审查，主执行用可重复案例核验其意见；审查报告不能代替浏览器与真实模型测试。

## 阶段与时间提案

预计首个本地可用版本主动工作约 15–29 小时，包含 S0–S4 各一次有限高级阶段审查及一次相关修正复查（S3含最终对抗验收）；另留 4–8 小时修正缓冲。审查超出这些轮次立即重估，不能无声增加工时。低置信度，尚无本项目实测吞吐。按连续执行、资料/API及时就绪推测约 3–7 个自然日；这不是保证。公开部署另估，不暗算在内。

| 阶段 | 权重 | 主动工作估计 | 四个验收项 |
| --- | --- | --- | --- |
| S0 方案冻结 | 10% | 1–2h | 基础规则与仓库；可行性审查；用户确认产品技术边界；验收口径与本地提交决定记录 |
| S1 最小可用流程 | 35% | 4–8h | 真实文本输入；真实模型候选卡；确认编辑并保存；刷新后原文任务一致 |
| S2 重复使用 | 25% | 4–8h | 来源内重复处理；更正建议；完成重开编辑删除；导出与移动布局 |
| S3 对抗验收 | 20% | 4–8h | 固定集真实评测；关键边界回归；Astra审查闭环；真实浏览器完整流程 |
| S4 可交付材料 | 10% | 2–3h | 新目录按说明启动；合成演示与视频；限制与实测报告；用户试用及交付确认 |

各阶段四项均需相应 Astra 审查闭环才能算完整通过。S1 结束立即进行三组价值试用；未记录继续决定不进入 S2。S4 是交付复验，不能代替前期价值试用。

计算：阶段完成项/4；项目进度=权重×阶段比例之和。冻结后不得静默改变分母。阶段完成记录预计/实际/偏差/后续时间调整。用户批准前只报告暂定口径。
